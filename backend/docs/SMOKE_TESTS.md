# Смоук-тесты бэкенда (`backend/smoke_test.py`)

**Что это.** Один файл, который поднимает всё приложение в памяти (in-memory SQLite)
и прогоняет ~26 сквозных HTTP-проверок: регистрация → вход → JWT → CRUD → роли →
запреты. Не нужны ни PostgreSQL, ни запущенный uvicorn, ни сеть. Это ваш «предохранитель»:
любое изменение в коде проверяется одной командой за пару секунд.

---

## 1. Быстрый старт

```powershell
cd backend
venv\Scripts\Activate.ps1          # или source .venv/bin/activate на Linux/Mac
python smoke_test.py               # запуск всех проверок
```

Расшифровка вывода:
```
[OK  ] POST /auth/register -> 201          ← проверка пройдена
[FAIL] GET /users как не-admin -> 403      ← провал + рядом текст ответа (<- {...})
ИТОГ: 26 пройдено, 0 провалено
```
- **Код возврата 0** — всё зелёное. **1** — есть провалы (их список в конце).
- Провал почти всегда = реальный баг в коде/тесте, смотрите `hint` после `<-`.

Тесты изолированы (своя база на каждый запуск) — гоняйте хоть после каждой правки.

---

## 2. Как это устроено (чтобы не бояться править)

| Кусок | За что отвечает |
|---|---|
| `settings.DATABASE_URL = "sqlite+aiosqlite:///:memory:"` | Подмена БД **до импорта app.main** — иначе движок уже создастся с Postgres из `.env`. Порядок строк тут критичен! |
| `make_client()` | Создаёт таблицы, заводит админа (эмуляция lifespan) и возвращает httpx-клиент, «воткнутый» прямо в ASGI-приложение (`ASGITransport`). Никакого TCP/порта. |
| `app.dependency_overrides[get_db]` | Стандартный механизм FastAPI: вместо реальной сессии Postgres ручки получают сессию SQLite. |
| `check(name, condition, hint)` | Одна строка отчёта; результат копится в PASSED/FAILED. |
| `login()` / `auth()` | Хелперы: получить токен по form-data и собрать заголовок `Authorization: Bearer ...`. |
| `run()` | Собственно сценарий, разбит комментариями-блоками `---------- N. ... ----------`. |

Важная тонкость: **lifespan при ASGITransport не выполняется**, поэтому таблицы и
админ создаются вручную внутри `make_client()`. Новая модель подхватится
автоматически (`Base.metadata.create_all`), если она импортирована в `models/__init__.py`.

## 3. Добавить тест под НОВУЮ РУЧКУ (пошагово)

1. Реализуйте ручку по чек-листу из `README.md` (model→schema→repo→service→deps→router).
2. Откройте `smoke_test.py`, найдите блок нужной темы (или создайте новый `# ---------- 6. Игры ----------`).
3. Вставьте проверки по шаблону:

```python
# Успешный кейс: создаём сущность авторизованным запросом
r = await client.post(f"{V1}/games", json={"title": "Doom"}, headers=auth(admin_token))
check("POST /games -> 201", r.status_code == 201, r.text)
game_id = r.json()["id"]                       # id пригодится для следующих проверок

# Негативные кейсы — обязательны минимум два: без токена и с чужой ролью
r = await client.post(f"{V1}/games", json={"title": "Doom"})
check("POST /games без токена -> 401", r.status_code == 401, r.text)

r = await client.delete(f"{V1}/games/{game_id}", headers=auth(player_token))
check("DELETE /games как player -> 403", r.status_code == 403, r.text)
```

Правила хорошего смоук-теста:
- **Одна проверка = одно утверждение** (`check(...)`, а не `and` на три условия).
- Всегда тестируйте **4 угла**: happy path, 401 (нет токена), 403 (не та роль), 404/422 (кривые данные).
- `hint=r.text` — чтобы при провале сразу видеть ответ сервера.
- Все проверки идут в одном общем клиенте: учитывайте состояние (юзер удалён — его токен мёртв).
  Нужен «чистый» актёр — регистрируйте нового (блок 4 делает так `pure_player`).

4. Запустите `python smoke_test.py` — все старые проверки обязаны остаться OK.

## 4. Добавить тест под НОВУЮ СУЩНОСТЬ целиком

1. Модель → импортируйте её в `app/models/__init__.py` (без этого `create_all` её не увидит!).
2. Первая проверка новой сущности обычно «CRUD по кругу»: create → get → update → delete → get(404).
3. Проверки FK-связей: создание дочерней сущности с несуществующим родителем → ожидайте 400/404/422.

## 5. Типичные проблемы

| Симптом | Причина / решение |
|---|---|
| `ModuleNotFoundError: aiosqlite` | `python -m pip install -r requirements.txt` (aiosqlite там есть). |
| Тесты падают на логине админа | Поменяли `ADMIN_USERNAME/PASSWORD` в `.env`? Тест берёт их из `settings` — сверьтесь. |
| `Unable to create process... pip.exe` | Скопированный из другого проекта venv. Пересоздайте: `python -m venv venv`, ставьте через `python -m pip`. |
| Новая проверка падает, хотя в Swagger работает | Забыли переопределить новую зависимость? Или ручка требует роль — используйте соответствующий токен. |
| Хотите видеть SQL при дебаге | Временно: `create_async_engine(..., echo=True)` в `database/session.py`. |

## 6. Дальше: превращение в настоящие pytest-тесты

Смоуки — быстрый контур «не сломалось ли вообще». Для глубоких тестов (unit на сервисы,
фикстуры) переходите на pytest:
```bash
python -m pip install pytest pytest-asyncio
```
Файл `tests/test_users.py` может переиспользовать `make_client()` как фикстуру:
```python
import pytest
from smoke_test import make_client   # или вынесите её в tests/conftest.py

@pytest.fixture
async def client():
    c = await make_client()
    yield c
    await c.aclose()
```
Прогрессия: держите зелёным `smoke_test.py` (он дешёвый), pytest наращивайте
под каждую нетривиальную бизнес-логику в `services/`.
