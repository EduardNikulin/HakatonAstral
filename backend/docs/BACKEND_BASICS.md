# Бэкенд: теория без ресторанов и метафор

Краткая выжимка. Полное обучение — в чате с ассистентом; здесь только база,
которая нужна, чтобы ориентироваться в коде.

## 1. Что вообще такое бэкенд и как приходит запрос

Бэкенд = программа, которая крутится на сервере, слушает порт (у нас 8000) и
отвечает на HTTP-запросы. Один запрос проходит путь:

```
браузер/фронт -> URL + метод (GET/POST/PATCH/DELETE)
             -> FastAPI находит функцию по адресу (роутер)
             -> функция читает заголовок Authorization, параметры, тело JSON
             -> код делает запрос к базе данных
             -> ответ: JSON + числовой статус (200 ок, 201 создано,
                400 некорректные данные, 401 не вошёл, 403 нет прав,
                404 не найдено, 409 конфликт, 422 схема не сошлась, 500 баг)
```

Статусы важны фронту: он по коду решает, показать ошибку или продолжить.

## 2. Слои проекта: каждый файл отвечает за ОДНО дело

Порядок вызова всегда сверху вниз, обратных стрелок нет:

| Папка | Что внутри | Правило |
|---|---|---|
| `app/api/v1/*.py` (роутеры) | функции-обработчики URL | только принять запрос -> вызвать сервис -> вернуть JSON. Никакого SQL и бизнес-правил |
| `app/api/deps.py` | зависимости для роутеров | собирает цепочку БД+репозиторий+сервис в один аргумент; проверяет токен (`get_current_user`) и роль (`require_admin`) |
| `app/services/*` | бизнес-правила | «нельзя два одинаковых логина», «админ не удаляет сам себя». Работает с репозиторием, про HTTP ничего не знает |
| `app/repositories/*` | все запросы к БД | единственный слой, где есть `select/insert/update/delete`. Возвращает объекты-строки |
| `app/models/*` | описание таблиц | класс = таблица, атрибут = колонка. Только типы и связи |
| `app/schemas/*` | описания форм ввода/вывода | Pydantic сам проверяет JSON и сам не отдаёт лишнего (пароль не попадает в ответ) |
| `app/core/` | настройки и шифрование | `.env` через config.py; JWT и bcrypt в security.py |
| `app/main.py` | сборка всего | создаёт приложение, подключает роутеры и CORS, при старте заводит админа |
| `migrations/` | история изменений таблиц | Alembic сравнивает models/ с базой и генерирует ALTER TABLE |

Зачем разделять: меняется правило — правим сервис; меняется колонка — правим
model + миграцию; меняется формат ответа — схему. Роутеры и остальное не
трогаем. Новый объект (например «Пост») = новые файлы по одному в каждую папку
+ одна строка `include_router` в `api.py`. Чек-лист из 7 шагов — в README.md.

## 3. Авторизация одной страницей

1. `POST /auth/login` принимает username/password (form-data), сверяет пароль
   с хешем в БД (bcrypt), выдаёт `{"access_token": "<JWT>"}`.
2. JWT — это подпись: внутрь заложены id пользователя, роль и срок годности;
   подпись ставится секретом из `.env`, подделать без секрета нельзя.
3. Фронт сохраняет токен и в каждый следующий запрос кладёт заголовок
   `Authorization: Bearer <токен>`.
4. На сервере `deps.py`: расшифровать -> найти пользователя в БД -> проверить
   роль. Не совпало — 401/403 ещё до входа в функцию роутера.
5. Роли: `admin / author / player`. Регистрация всегда даёт player; повышение
   только через `PATCH /users/{id}/role` от имени admin.

## 4. Проверка без запуска сервера

`python smoke_test.py` поднимает приложение в памяти на SQLite и прогоняет все
ручки сквозными проверками (26 OK = зелёное). Инструкция и способ добавить тест
под новую ручку — в `SMOKE_TESTS.md`. Это ваш предохранитель после любой правки.

## 5. Glossary (термины, которые встречаются в коде)

- **endpoint / ручка** — URL + метод, например `GET /api/v1/users`.
- **DI (зависимости)** — механизм FastAPI: функция-хелпер подставляет в роутер
  готовые БД-сессию/сервис вместо ручного создания.
- **ORM** — библиотека SQLAlchemy: вы пишете классы, она превращает в SQL.
- **миграция** — файл с изменением структуры таблиц, применяется `alembic upgrade head`.
- **asynchronous (async/await)** — сервер ждёт базу, не блокируя другие запросы;
  поэтому все функции в слоях помечены `async`.
